Swift concurrency, explained

Swift concurrency is built around the idea that work can wait without holding up the whole program. This guide walks through the parts that matter most in practice.

Async functions can suspend without blocking a thread, so the system can run other work while they wait for results.

A small example helps: a function that downloads an image awaits the network and returns when the bytes arrive.

Actors serialize access to their mutable state, so data races are caught by the compiler instead of appearing in production.

Actors do not remove the need to think about ordering, but they make the shape of shared state explicit and easier to review.

Structured concurrency keeps child tasks inside the scope that created them, so cancellation and errors flow in a predictable way.

Many apps start with one task per screen and then discover that a task group is a clearer way to fan out repeated work.

Reading a long chain of callbacks is hard, and the await keyword turns the same logic into a straight line of code.

Sendable is the protocol that marks values safe to pass across concurrency domains without copying hidden shared state.

The compiler checks Sendable conformance for most value types automatically, so you rarely write it by hand.

Migration is usually gradual: turn on the stricter checks for one module, fix the warnings, then move to the next module.

Task groups let a function start many child tasks at once and collect their results as each one finishes.

Results can arrive in any order, so code that depends on sequence should sort or index the values it collects.

Timeouts are not built in, but a race between a sleep and the real work gives the same effect with a few lines.

The main actor runs user interface updates, so code that touches views should be marked with that actor.

Moving slow work off the main actor keeps scrolling smooth, but every value that crosses back must be safe to send.

Continuations bridge older callback APIs into async code, letting a completion handler resume a suspended function once.

Wrapping a callback API takes care: resuming twice is a runtime error, and never resuming leaves the caller waiting forever.

Logging inside actors is cheap, but avoid awaiting network calls while holding state that other callers need right away.

Cancellation is cooperative: a task is told it was cancelled, and it must check that flag at safe points to stop early.

Checking cancellation in long loops keeps the app responsive when a user leaves a screen before the work finishes.

Testing concurrent code is easier when each actor is given its dependencies at creation time instead of reaching for globals.

In short, concurrency in Swift is a set of guarantees. Learn them one at a time and the rest of the model follows.
