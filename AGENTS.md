## Overview

macOS menu bar companion app. Lives entirely in the macOS status bar (no dock icon, no main window). Clicking the menu bar icon opens a custom floating panel with companion voice controls. Uses push-to-talk (ctrl+option) to capture voice input, transcribes it on-device with Apple Speech, and sends the transcript + a screenshot of the user's screen to Claude through the local Claude Code CLI (the user's Claude subscription). Claude's reply is spoken with the built-in Mac voice. A Claude-orange spark companion follows the cursor, spins while Claude is thinking, shows helper workers as orbiting minis, and can fly to and point at UI elements Claude references on any connected monitor.

The product is now **Vello** (called Theo until November 2026): a Mac app with a main window (bots, teams, routines, connectors, Settings) plus **Pointer Assistant** (called Clicky until then), the voice and screen companion. It installs as `/Applications/Vello.app` (bundle `com.personal.clicky`, executable `Clicky`); an installed `Theo.app` becomes `Vello.app` on its next update (`UpdateFeed.installScript` keeps the new app's file name, `install.sh` upgrades a `Theo.app` in place).

**Names in this file and in the code:** "Theo" and "Clicky" below, and in type names, files, defaults keys (`v2.…`, `theo.…`), Keychain services, the data folder (`~/Library/Application Support/Theo`), the bot ids `theo` / `clicky` and protocol tags like `[CLICKY: …]`, are the internal names and stay as they are so existing installs keep their settings and updates. Everything a person sees says Vello and Pointer Assistant: write new user-facing strings with those names. Migrations from the old names: `ClickySettings.migrateAssistantNameIfNeeded` (a saved "Theo" becomes "Vello"), `BotImport.upgrade` (the starter bot named Theo becomes Vello), `ClickyTeamStore.renameTeamCategoryOnce` (the team category "Clicky" becomes "Pointer Assistant"). "hey vello" wakes it, and "hey theo" still does for now (`WakeWordMatcher.defaultPhrases`).

No proxy server and no analytics. Harnesses (T3 Code, Claude Code, Codex, Cursor, OpenCode, Grok, Gemini) run on the owner's own subscriptions. Keys are optional: any provider in Settings › Models & API keys can drive a bot, Theo, Clicky, a harness or a voice, and stays in the Keychain. Never print or log a key.

Every call starts with the end of that bot's text chat, earlier calls included (the transcripts `recordCall` saved), newest first, as much as the call's brain has room for (`CallPrompt.carriedOverCharacters`: a quarter of what its context window leaves after the instructions and the answer, at most 40,000 characters; `CallPromptText.recentChat`), so a call remembers what the last one said; a bot whose engine lost its session starts over with up to 16,000 characters of its chat (`BotsStore.startOverCharacters`, Windows and Linux `START_OVER_CHARACTERS`). `TheoCallSession` runs mic → `VoiceActivityGate` → ears (`SarvamCallEars` realtime, then standard socket; `AppleCallEars`) → a `ConversationBrain` (`ClaudeConversation`: one `claude -p` kept open, multi-turn, interruptible; any other brain: `OneTurnConversation`, one streamed request per turn; `ConversationBrains.make` picks, `CallSettings.model` unset means Sonnet with Claude Code, else Clicky's brain) → `CallSpeechChunker` → voice (`SarvamCallVoice` socket; `AppleCallVoice`). Turn-taking: the ears' words are held until a real pause (`waitForTheEndOfTheTurn`): Settings › Voice › Patience (`v4.call.patienceSeconds`, default 1.5 s), longer when the words sound unfinished, shorter for a clear question (ClickyCore `Voice/CallTurnTaking.swift` `CallTurnEnd`); talking again during the wait carries on the same turn. Words the ears write down while Vello's voice plays with the gate shut, or just after that are mostly what it said (`CallEcho`), are its own voice coming back and are dropped, never taken as the owner cutting in. Only the voice near the Mac counts (`v4.call.nearVoiceOnly`, default on; ClickyCore `CallNearVoice`): a call runs with the automatic gain off (`AudioEngineHub.startVoiceProcessingCapture(keepsDistanceInLoudness:)`), a stretch of speech counts only when it's within 9 dB of the owner's usual level (the middle of the last twelve near stretches, loosening after 15 s with nothing near, never past 14 dB), only a stretch within 4 dB of that level or louder teaches it (`CallNearVoice.learnsWithinDecibels`, so voices just let through can't drag it down), and the ears' words with no near voice in the last 3.5 s are someone else's and dropped. A sound alone never throws away an answer Vello is still writing: only the owner's words do (`ownerWordsCameDuringTheAnswer`, two words in a partial or any final); a sound over Vello's playing voice still stops it at once. Only new words cut in (ClickyCore `CallCutIn`): the ears repeating words already taken are dropped, an answer not yet heard starts over with the added words at most twice (`mostRestartsPerAnswer`; later words wait for it and are answered next) and its first try leaves the conversation's memory (`ConversationBrain.forgetTheTurnBeingAnswered`, ClickyCore `Brain/ForgottenTurn.swift`, `BrainCLIRunner.forgetTurn`), a stretch the ears hand over again while a turn is held is added once (ClickyCore `CallHeldWords`), and partials still coming keep the turn open, but for at most 1.5 s past the wait (ClickyCore `CallQuietLimit.releasesTurn`, since people talking near the Mac keep partials coming too). If none of an answer to the owner has sounded 2.5 s after the turn was let go, Vello says a few words first ("One sec.", "हाँ, एक सेकंड।", `CallQuietLimit.acknowledgement`). A turn the brain gives no answer to (a local server not running, a signed-out CLI, an error) is said out loud with which brain and why, the first time in full and then briefly (ClickyCore `CallBrainFailure`), never left silent, and logged as `📞 Call: <brain> gave no answer`. Saying Vello's name in Listen mode ends it (`CallListenMode.callsVelloByName`; another bot's call answers to its whole name and each word of it but everyday ones, "Observer" for Super Neutral Observer, `CallListenMode.names(forBotNamed:)`); a "what do you think" without the name answers and keeps listening. Patience and that switch are also in the call window's header menu. Thinking models (Qwen 3.x and the like) never have their thinking spoken or shown: ClickyCore `Brain/ThinkingText.swift` takes out a `<think>` block (one the reply opens with, one it starts in the middle of with only the closing tag, one that never closes), `reasoning_content` is never read as text, and a model that may start mid-think is held until it's sure unless the server is seen separating its reasoning. `APIChat.streamRound` applies it to every bot chat and call on an API key, `OneTurnConversation` once more for any brain, and an OpenAI-style call asks for `APIChat.roomForThinkingTokens` (16,384; `max_completion_tokens` on OpenAI itself) so the model can finish thinking. ## Architecture

- **App Type**: Menu bar-only (`LSUIElement=true`), no dock icon or main window
- **Framework**: SwiftUI (macOS native) with AppKit bridging for menu bar panel and cursor overlay
- **Pattern**: MVVM with `@StateObject` / `@Published` state management
- **AI Chat**: Claude via the Claude Code CLI (`claude -p` in stream-json mode, see `ClaudeCodeBridge.swift`), signed in with the user's subscription. Model is a Claude Code alias (`sonnet` default, `opus` optional)
- **Speech-to-Text**: Apple Speech (on-device) by default via `VoiceTranscriptionProvider = apple` in Info.plist. AssemblyAI/OpenAI providers remain but need their own backend
- **Text-to-Speech**: Built-in Mac voice via `AVSpeechSynthesizer` (`SystemVoiceTTSClient.swift`). `ElevenLabsTTSClient.swift` is kept but unused
- **Screen Capture**: ScreenCaptureKit (macOS 14.2+), multi-monitor support
- **Voice Input**: Push-to-talk via `AVAudioEngine` + pluggable transcription-provider layer. System-wide keyboard shortcut via listen-only CGEvent tap.
- **Element Pointing**: Claude embeds `[POINT:x,y:label:screenN]` tags in responses. The overlay parses these, maps coordinates to the correct monitor, and animates the blue cursor along a bezier arc to the target.
- **Concurrency**: `@MainActor` isolation, async/await throughout
- **Analytics**: None. `ClickyAnalytics.swift` keeps its methods as no-ops so call sites compile

### Claude Code Bridge

`ClaudeCodeBridge.swift` replaces the old HTTP client. Per request it launches the `claude` CLI with `-p --input-format stream-json --output-format stream-json --include-partial-messages --tools "" --strict-mcp-config --disable-slash-commands --no-session-persistence`, writes one user message (base64 screenshots + text) to stdin, and parses `stream_event` text deltas plus the final `result` event from stdout. Prior turns are folded into the message text because stream-json input can't carry assistant turns. Never pass `--bare`: it disables OAuth/keychain auth, which breaks subscription sign-in. The CLI must be signed in once with `claude auth login`.

### Hands-Free Sessions

Double-tapping the push-to-talk shortcut (or the panel button) starts an always-on mic session. `HandsFreeListeningSession` runs its own `AVAudioEngine` with voice processing (echo cancellation) and on-device `SFSpeechRecognizer`, splitting speech into utterances after ~1.1s of silence and restarting the recognition request each time. `HandsFreeVoiceCommand` matches whole utterances against local command phrases (wait/go/capture/slower/faster/done) so they act instantly; everything else goes to Claude. "wait"/"stop" also fire on partial transcripts while the buddy is talking or thinking. Non-command speech heard while the buddy was speaking is dropped as likely echo, except with echo cancellation on, where three or more words that aren't mostly its own (ClickyCore `Voice/HandsFreeBargeIn.swift`) are a new instruction and replace what it was doing. Escape (seen via the listen-only event tap) stops speech, cancels the response, and ends the session. Captures are full-resolution PNGs in `~/Pictures/Clicky/Session …/`.

### Wake Word (P7)

"Hey Claudia" / "Hey Clicky" (`v2.wake.enabled`, default on; `v2.wake.phrases`). `WakeWordController` keeps a small `AVAudioEngine` input tap (no voice processing) feeding ClickyCore's `WakeWordRecognitionPipeline`: an energy gate (0.6 s pre-roll) so the recognizer idles in silence, an `SFSpeechRecognizer` that is always on-device (no on-device support → off, never a server fallback), requests restarted every 50 s and after finals. `WakeWordMatcher` accepts the phrase only at the start of an utterance segment (request start or after a ≥ 0.6 s pause), with fuzzy ASR spellings; `WakeWordGate` debounces 2 s and ignores matches while Clicky talks, within 1.5 s after, or when Clicky just said the name (EchoGuard words). After a wake the turn is heard on the same request until `UtteranceEndRule` (the hands-free 1.1 s rule) ends it, then goes through `sendTranscriptToClaudeWithScreenshot`. Who a phrase calls is ClickyCore `WakeTarget`: Vello's names ("hey vello", "hey theo", "hey <the name the owner gave it>") call Vello, so Pointer Assistant isn't woken: the words after the name are still heard by the wake listener, then a call with Vello starts (`TheoCallController.start(activates: false, openingWords:)`, focus left alone) with them as its first turn, so "hey vello, find my mails" reaches the one with the apps; nothing after the name still opens the call, Escape doesn't. With the Vello product off they wake Pointer Assistant as before. With Vello on, "hey pointer" and "hey claudia" call Vello too ("hey pointer assistant", the "assistant" dropped from the turn), and so do push-to-talk (its words are the call's first turn) and hands-free (double tap or the panel button), since Pointer Assistant is Vello's hands now (`VelloHands.answersEveryVoice`); the sidebar then hides Pointer Assistant's chat, team and pill, and its product and Settings page are called "Vello's hands". With Vello off they wake Pointer Assistant as before. The listener yields the mic whenever push-to-talk / hands-free claim it on `AudioEngineHub` and pauses while another app runs mic input (CoreAudio process objects, polled every 2 s), the default input is a Bluetooth headset, or the screen is locked / asleep. "stop listening" / "start listening" flip the setting. Debug inbox: `wakeStatus`, `wakeFeed {path}`.

### Full voice control (P8)

- **Wake diagnosis**: `wakeStatus` adds `errorsByCode` (recognizer `domain:code`; 1110 no-speech, 216/301 cancel and 203 retry are benign: not in `recognizerErrors`, no backoff), `nearMisses` (in memory: "hey <second word>" counts for greetings that didn't wake, nothing else kept), the listening `device` (same mic push-to-talk last used, unless Bluetooth; `PushToTalkInputDeviceRecord`), `deviceSampleRate`, `inputFormat`/`conversion` (input always converted to 48 kHz mono float32, `WakeAudioFormat.swift`), gate levels (`noiseFloorDb`, `openThresholdDb`: the gate's floor is the 20th percentile of the last 8 s, threshold floor+8 dB, never below -72), `makeUpGainDb` (quiet mic gain up to +20 dB for the recognizer only), pre-roll 1.0 s, and the locale chooser (`v2.wake.locale` auto | en-IN | en-US; auto moves to the other on-device English locale when ≥ 50% of the last 12 requests failed, at most once per 10 min, between turns).
- **Follow-up window** (`WakeFollowUp.swift`, `v2.wake.followUpSeconds`, default 10): after a wake turn's answer finishes (nothing thinking / speaking / acting for 0.5 s), the wake pipeline takes any words as a command without the wake word; "that's all" / "thanks that's it" / silence end it, Escape / push-to-talk / hands-free cancel it; EchoGuard drops utterances made mostly of Clicky's own recent words. Notch shows "listening…". Wake turns only (a fast-path confirm or dictation also keeps it open).
- **Local fast path** (`ClickyCore/Voice/VoiceFastPath.swift` parser + `VoiceFastPathPolicy`; app `Voice/VoiceCommandController.swift`, `Voice/VoiceFastPathExecutor.swift`; `v2.voice.fastPath`): volume / mute, brightness (built-in displays only), media keys (never when Safari is in front or a window shows Netflix unless named), window snap / maximize / minimize / move to screen N (screens numbered left to right), switch / open app, open file or folder (home top level, the projects folder, /Applications; protected folders only with `v2.code.searchProtectedFolders`), tabs / back / forward / copy / paste / select all, scrolling, Mission Control, show desktop, read selection aloud, dictation ("type what I say" … "stop typing"), screenshot, lock (confirm by spoken yes or the card). Same `ActionTierClassifier` tiers; the spoken command is its own confirm except lock and closing unsaved work. Not found on the Mac → the same turn goes to Claude. Each action is a small `.actionTask` record and a 1–3 word acknowledgement. Debug inbox: `voiceCommand {text, dryRun}`, `voiceStatus`, `wakeFeedBatch {paths, locale?}`, `wakeFeedChain {path, locale?}`.

### Live Marks

Claude can draw circles, arrows, and numbered step badges on the overlay by adding `[MARK:kind:x,y:label:screenN]` tags (kind = `circle`, `arrow`, or a step number) right before the final `[POINT:...]` tag. `LiveScreenMarkTagParser` strips every MARK tag (even malformed ones, so they're never spoken) before the POINT parser runs, caps marks at 6, and `CompanionManager` maps them from screenshot pixels to global coords the same way POINT does. `LiveScreenMarksOverlayView` draws them inside each screen's `BlueCursorView`, staggered in response order. Marks clear on the next question, on Escape, on the hands-free "clear" command, or 20s after speech ends; transient-mode overlays stay up while marks are showing.

### Spark Companion and Helper Workers

The old blue triangle and spinner are replaced by `ClaudeCompanionView`: an orange spark (`ClaudeSparkShape`, drawn in code) that breathes while idle and spins while `voiceState == .processing`. Flight/pointing logic in `BlueCursorView` is unchanged; the spark just sits at `cursorPosition`. Overlay colors (bubbles, waveform, live marks) use `DS.Colors.overlayCompanionOrange`. Idle CPU: the spark is a Core Animation layer tree (`CompanionSparkLayerView`), so breathing/spin/orbit run in the render server; cursor following runs on one shared `Perf/CursorFollowDriver` loop (60 Hz while the pointer moves plus 1 s linger, a 10 Hz poll when still, woken by mouse-moved monitors; cadence logic is ClickyCore `CursorFollowCadence`) that only writes `CursorFollowPosition` when it changed, and only the `CursorFollowReader` leaves observe it. Never add `TimelineView(.animation)` / `repeatForever` to always-present overlay views, never put a SwiftUI `.animation` on the followed position (it re-animates at the display's full rate; the ride is eased per tick in `SparkScreenLayer.easedRidePosition`), never fill the full-screen overlay with a colour (even 0.001 alpha makes WindowServer blend the whole screen), only the screen with the pointer moves its spark, and never assign unchanged values to `@Published` state on timers. The notch reads the window list for full screen at most every 5 s, or at once on a Space or app change. Debug inbox `perfStatus` reports body evaluations, loop ticks and state writes per second.

What orbits the spark comes from `CompanionActivitySource` objects registered with `CompanionManager.addCompanionActivitySource`; their workers are merged and capped at 4 visible (`CompanionActivityLimits`). Two sources exist: `CompanionWorkerRunner` (real) and `SimulatedCompanionActivitySource` (driven by the DEBUG-only "Companion" row in the panel: Think toggle and 0–4 workers).

Helper workers: the main request may reply with a short heads-up plus `[WORKER:short title:task prompt]` tags. `CompanionWorkerTagParser` strips them (max 8). `CompanionWorkerRunner.runWorkers` runs each as its own `ClaudeCodeBridge` request with model `haiku` (`workerClaudeModel`), at most 4 concurrently with the rest queued, in a task group that is a child of the response task, so Escape / "stop" / a new question cancels every worker (the bridge terminates each CLI process). Results are folded into a second main-brain request (`makeMainBrainPromptWithWorkerResults`) that produces the final spoken answer with MARK/POINT tags. One round of workers per question. The main brain keeps the user's chosen model.

### Computer-use actions (P7)

When the owner asks Clicky to *do* something ("open chrome and google this", "open the second link", "highlight the important facts", "summarize the article on screen"), Claude answers with one `<actions>{"goal":…,"steps":[{"do":"open_app",…}],"done":false}</actions>` block (grammar: `ClickyCore/Actions/ActionDSL.swift`; prompt: `ActionsPromptSection`, gated by `v2.actions.enabled`). `Actions/ActionTaskController.swift` runs it as an observe → act loop: each step is resolved read-only (`ActionExecutor.resolve`), classified by `ActionTierClassifier` (free / 1.5 s countdown / confirm by spoken yes / refused; hands-free, so confirm is only for buttons that send, post, buy, pay, book, delete, discard, merge, deploy, uninstall or sign out, and the owner's own words naming that button ("delete it", never for money) make it a countdown; Save, OK, Apply, Allow, System Settings outside Privacy, Vello's own main window and close/quit/save keys are the countdown. While a step waits, the wake listener's follow-up window stays open so a spoken yes is enough (`keepFollowUpOpen`), Vello's relayed "Yes, …" counts (`ActionConfirmReply.parseRelayed`), and mouse moves for 2.5 s after a click on the card don't cancel), then performed AX-first with tagged synthetic events only as fallback. Unless the block says `done`, once the batch ran and the answer finished speaking, the same request is asked again with the step results and a fresh capture (`ActionTaskLoop.continuationMessage`); max 12 steps per task. "stop", Esc, Cancel, any other utterance, and any physical input while steps run (`ActionInputMonitor` + `ActionCancelLogic`) cancel; a cancelled task also stops its own "look again" turn in flight, so its answer can't start the old goal over, and its report tells the brain a newer request replaced it. Return after typing follows `ActionReturnRule` (searches and prompt boxes yes, messages wait for "send", documents no); a Return step on a selected item that isn't a text field (a Spotify song, a Finder file) is pressed, after the countdown when the focus can't be read (`ActionReturnRule.keyDecision`). Password/payment fields, security prompts, terminals, privacy settings, Clicky's own panels and overlays, and Netflix (unless named) are refused; Safari only with `v2.actions.leaveSafariAlone` on (default off). Theo's own titled main windows (`TheoMainWindows`: Home, Settings, Agents, Setup) are in captures and the window stack, and read from the inside (`Grounding/OwnWindowAccessibility.swift`: the same `AXEnumerator` walk over AppKit's in-process accessibility objects, no IPC, elements without an AX node), so Clicky sees, lists and points at them (Electron apps such as the Claude app only ever get AXManualAccessibility, never AXEnhancedUserInterface, whose false → true tore their tree down for that ask, `EnhancedUserInterfacePolicy.flagWrites`; a cold-path ask whose front window has under 8 AX elements waits up to 0.9 s for OCR, ClickyCore `ColdPathOCRWait`); a click, key or typing there gets the countdown, and nothing there is ever asked over AX (it would wait on Theo itself). The spark waits for Accessibility, Screen Recording and the mic, not the screen-content picker (a good capture warm-up records that one), and is a non-activating panel so it shows over other apps' full-screen Spaces. The task is an `.actionTask` AgentRecord (live `actionSteps` in the notch and dashboard). When it ends, ClickyCore `ActionTaskReport` says what it did in plain words: that goes into Clicky's conversation history (`rememberActionTaskOutcome`), so the next question knows what was opened and clicked, and back to Theo when he ordered it (`orderClicky` waits for an earlier order's steps to end before starting, reports only once the steps have ended, and passes a yes or no said on a call to a step waiting for one). Orders take turns (`BotsStore.clickyOrderLine`, one `ClickyOrderTicket` each, done once it reported): each waits for the ones before it given from the same owner words, while an order given after the owner said something new replaces them (ClickyCore `Team/ClickyOrderReplacement.swift`: older orders are dropped, a turn answering one is stopped and its steps cancelled, reported as replaced), an order said again while the same one is still going is answered "Already on it.", and a turn the owner started is waited on for at most 30 s. A block whose steps couldn't be read (a click on words instead of a number) gets one more look even when it said done (`ActionTaskLoop.lastBlockHadUnreadableSteps`), and the report names the steps that didn't run. Clicky's own Esc and shortcuts carry `SyntheticEventTag`, so `PushToTalkKeys` never takes them for the owner's Esc; a shortcut with ⌘⇧⌥⌃ lets go of each modifier after it (`ActionExecutor.postKey`), and a step waits up to 1 s for modifiers to be up before saying one was held. Background input (`BackgroundInput.isActive`) is only for Clicky's own screen while the owner's pointer isn't on it, and only for targets on that screen (`staysInBackground`); on the owner's screen the app comes forward and the click is real. Debug inbox: `actionsStatus`, `actionsCancel`, `actionsRun {steps, dryRun}`.

### Article highlights and notes (P8)

"highlight the important things / make notes / study this article": Claude first sends `{"do":"read_article"}`; `Article/ArticleReader.swift` finds the article window (the frontmost browser, even behind a terminal or Clicky's panels — ClickyCore `ArticleWindowChoice`), walks its AXWebArea in reading order (AXStaticText runs; nav/banner/footer/aside landmarks and controls skipped; only the AXLandmarkMain / AXDocumentArticle subtree when present) and joins the runs (`ArticleTextAssembler`, ≤ `v2.article.maximumCharacters`, default 30k). Too little AX text → scroll + OCR of the viewport page by page (tagged scroll events only, scrolled back; `v2.article.scrollOCRFallback`). The text goes back in the observe turn (`ActionTaskLoop.pendingArticleText`), and Claude answers with one block: `highlight` with 5–8 verbatim sentences + `notes {title, summary, items:[{note, quote}]}`. Sentence targets (`ActionHighlightTarget.isSentence`) are drawn by `Article/ArticleHighlightController.swift`: each sentence is matched on a letters-and-digits skeleton (`ArticleSentenceMatcher`, approximate fallback), mapped to per-run ranges, measured per line (`ArticleTextBounds`: AXBoundsForRange → text markers → run frame; wrapped ranges word by word → `ArticleLineFragments`), else fuzzy-matched across OCR lines of the viewport. Soft yellow strokes (no outline) live in a click-through overlay over the viewport; a 10 Hz timer runs only while highlights / the panel exist and moves them by their anchor run's AXFrame delta (reflow → remeasure); off-screen ones are numbered ticks in the right margin (`ArticleHighlightLayout`). The notes panel is non-activating, docked beside the window on the side with the most free space (`ArticleNotesDock`, never over the article column), follows the window, hides while another app is in front; clicking a note does AXScrollToVisible on its run. "save my notes" / `[NOTES:save]` / Save → `~/Clicky Notes/<title>.md` + PDF via WhiteboardExporter (`ArticleNotesExport`). Debug inbox: `articleRead`, `notesStatus`, `notesSave`.

### Key Architecture Decisions

**Menu Bar Panel Pattern**: The companion panel uses `NSStatusItem` for the menu bar icon and a custom borderless `NSPanel` for the floating control panel. This gives full control over appearance (dark, rounded corners, custom shadow) and avoids the standard macOS menu/popover chrome. The panel is non-activating so it doesn't steal focus. A global event monitor auto-dismisses it on outside clicks.

**Cursor Overlay**: A full-screen transparent `NSPanel` hosts the blue cursor companion. It's non-activating, joins all Spaces, and never steals focus. The cursor position, response text, waveform, and pointing animations all render in this overlay via SwiftUI through `NSHostingView`.

**Global Push-To-Talk Shortcut**: Background push-to-talk uses a listen-only `CGEvent` tap instead of an AppKit global monitor so modifier-based shortcuts like `ctrl + option` are detected more reliably while the app is running in the background.

**Shared URLSession for AssemblyAI**: A single long-lived `URLSession` is shared across all AssemblyAI streaming sessions (owned by the provider, not the session). Creating and invalidating a URLSession per session corrupts the OS connection pool and causes "Socket is not connected" errors after a few rapid reconnections.

**Transient Cursor Mode**: When "Show Clicky" is off, pressing the hotkey fades in the cursor overlay for the duration of the interaction (recording → response → TTS → optional pointing), then fades it out automatically after 1 second of inactivity.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
- AppKit `NSPanel`/`NSWindow` bridged into SwiftUI via `NSHostingView`
- All buttons must show a pointer cursor on hover
- For any interactive element, explicitly think through its hover behavior (cursor, visual feedback, and whether hover should communicate clickability)

### Windows and Linux follow the Mac

- Every change to the Mac app gets the same change in `crossplatform/` (Rust in `crates/theo-core`, UI in `app/ui`, suite cases in `tests/`) in the same PR, wherever Windows and Linux have that feature. Where they don't have it yet (voice calls, the notch, see `crossplatform/docs/PLATFORMS.md`), the PR says so and that list names it.
- Run `cargo test --workspace` and the matching `python tests/suite.py <cases>` in `crossplatform/` before pushing. Windows builds publish themselves from green `main` runs of "Theo cross-platform", so a red Windows suite holds back every Windows release.

### Do NOT

- Do not add features, refactor code, or make "improvements" beyond what was asked
- Do not add docstrings, comments, or type annotations to code you did not change
- Do not try to fix the known non-blocking warnings (Swift 6 concurrency, deprecated onChange)
- Do not rename the project directory or scheme (the "leanring" typo is intentional/legacy)
- Do not test in the owner's real profile: use `--profile test` (docs/TESTING.md)

## Git Workflow

- Branch naming: `feature/description` or `fix/description`
- Commit messages: imperative mood, concise, explain the "why" not the "what"
- Do not force-push to main
